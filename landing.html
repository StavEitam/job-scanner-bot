why it exists

The gap between job boards and what you actually want

Global platforms don't cover Israeli boards. Israeli boards don't cover global platforms. And almost none of them let you filter structurally by the two things that matter most for a narrow search.

Coverage

No single tool spans both markets. LinkedIn/Indeed/Glassdoor miss Israeli boards entirely; Drushim and similar sites don't touch global postings.

Filtering

Experience and seniority aren't structured fields. They live inside free-text descriptions, in Hebrew or English — almost every board treats them as prose, not filters.

The fix

Scrapers find candidates, an LLM decides fit. Each source is queried with a simple keyword search; a Claude node reads every survivor in full before anything is sent.

how a /scan runs

Pipeline

Nothing runs on a timer. The whole chain fires only when triggered by a Telegram message, and every stage narrows the set further — cheap filters first, the expensive one last.

1

Telegram trigger on-demand only

/scan alone runs a default watchlist of roles; /scan Product Manager, GenAI searches exactly those. No cron — zero cost when you're not looking.

2

Parse requested titles

Splits the message into a list of roles and fans each one out to every scraper below.

3

Scrape in parallel 4 sources

LinkedInApify actor
IndeedApify actor
GlassdoorApify actor
DrushimIsrael, Hebrew
4

Merge & normalize

Four different field schemas collapse into one shape: job_id, title, company, location, link, description. job_id itself falls back through a chain — a real source ID, then the posting URL, then title+company — since not every source exposes a clean one.

✓

Keyword pre-filter $0, no AI

A plain regex rejects postings whose title unambiguously signals seniority — Senior/Director/VP/Head of, and Hebrew equivalents — before a single AI token is spent. Deliberately does not reject plain "Manager," which would false-positive on "Product Manager."

✳

AI match decision Claude Haiku, chunked

Deduplicates by job_id, then splits the survivors into fixed-size chunks sized from measured output cost per decision, not a guess. Each chunk is one Claude call returning a JSON array of decisions — n8n fires one call per chunk automatically, no custom loop needed.

Reads every posting, in Hebrew or English, against the requested titles — allowing synonyms, not just exact strings — plus a hard gate: reject anything senior, lead, or requiring more than the stated experience ceiling.

5

Dedup against Google Sheets

Every match is checked against a running log before delivery — nothing gets sent twice, ever, even across separate /scan runs weeks apart.

6

Sort by fit score, then deliver Telegram

Survivors are ranked by the AI's own 0–100 match score before sending, so the strongest fits land first — title, company, score, reasoning, link — and get logged with a status column for tracking applications.

cost & efficiency

Every number below is measured, not assumed

The first working version made one Claude call per posting. It worked, but scaled badly: minutes-long runs, and a system prompt (the full matching criteria) re-sent hundreds of times over. The fix was batching — and getting the batch size right required real token accounting, not a round-number guess.

~97% fewer AI calls on a full default-watchlist run — 10 calls instead of 322 — because the system prompt is paid once per chunk of jobs, not once per job.

Empirically measured ~182 tokens per AI decision (not the ~45 originally assumed — found by deliberately overflowing a small output budget and counting what actually fit).
8,000 max output tokens × 0.8 safety margin ÷ 182 ≈ 35 jobs per chunk — the batch size that fits without silent truncation.
322 unique jobs ÷ 35 ≈ 10 chunks = 10 API calls, each returning a full JSON array of decisions.

Why not one giant call

Packing all 322 jobs into a single prompt was tried first — it silently truncated mid-JSON past the model's output ceiling, dropping every job after the cutoff without an error. Chunking by measured token cost fixed it with zero jobs lost.

Cheap model, on purpose

Match/no-match + score + reason is a classification task, not open-ended generation — Claude Haiku handles it fully and keeps the whole run's cost negligible even at hundreds of postings.

design decisions

Choices that weren't defaults

Two-tier filtering

Cheap regex first, expensive LLM second — the two only overlap on ambiguous cases (seniority stated only in body text), which is exactly what needs judgment, not pattern matching.

Actually dynamic

The AI's matching criteria are built from whatever titles were requested that run, not a string hardcoded into the prompt — a one-off search for a role outside the default watchlist still filters correctly.

Two dedup layers, two jobs

Within a run: the same posting often surfaces under two searched titles — deduplicated by job_id before it reaches the AI. Across runs: a Sheet log stops the same posting from ever being re-sent, even weeks later.

Vetted, not first result

Each Apify actor was picked by comparing rating, review count, and real 30-day active usage — a few high-star actors turned out to have single-digit user counts.

What building it actually involved

Workflow automation

Designed a multi-stage n8n pipeline end-to-end — trigger, parallel fan-out, conditional filtering, chunked batch processing, and delivery — with no custom loop code, relying on n8n's per-item execution model instead.

API integration

Wired four independent third-party APIs (Apify actors) with mismatched schemas into one normalized shape; caught and fixed multiple guessed-field-name failures by verifying real input schemas directly rather than trusting form labels.

Prompt engineering & cost design

Moved from one-call-per-item to a measured, chunked batching strategy after diagnosing a silent output-truncation bug — sizing batches from empirically observed token cost per decision instead of an assumed number.

Debugging under partial information

Root-caused a token-count discrepancy (322 sent vs 321 decisions returned) by reconstructing the pipeline's dedup math from raw execution data, distinguishing a real bug from expected/negligible loss.

Bilingual data handling

Built matching logic (regex pre-filter and LLM prompt) that treats Hebrew and English job postings as first-class, including seniority-signal detection in both languages.

—

Comeet-hosted career pages — a dedicated actor exists but scrapes one company at a time rather than searching broadly; needs a maintained company list, not yet wired in.

—

Telegram/WhatsApp job groups — no ready tool; would need a custom listener feeding the same AI gate.

—

Still developer-facing UX — no /help, no way to persist a custom role list without retyping it, no 👍/👎 feedback loop to teach the filter over time.

—

No spend guard yet — nothing currently caps Apify/Claude usage per day, worth adding given a mid-build session where Apify credits ran out unexpectedly.

—

Cross-source dedup is exact, not fuzzy — the same real posting on two different boards with two different job_ids is currently sent twice.
