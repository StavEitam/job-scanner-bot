how a /scan runs

Pipeline

Nothing runs on a timer. A Telegram message fires the whole chain, and each stage narrows the set: cheap filters first, the expensive one last.

/scan runs a default watchlist; /scan Business Analyst, Customer Success searches just those. Locked to one Telegram user.

Splits the message into a list of roles, one per scraper.

4

Merge and normalize

Four schemas collapse into one shape: id, title, company, location, description, posted date.

✓

Keyword pre-filter free, no AI

A regex rejects obvious senior titles (Senior, Director, VP, Hebrew equivalents) before a single AI token is spent.

✳

Ranked by fit score, sent to Telegram, logged with a status column.

cost and efficiency

Numbers from real runs, not guesses

The first version called Claude once per posting. It worked but ran slow, and the system prompt got billed hundreds of times over. Batching fixed both.

Why not one giant call

All 322 jobs in a single prompt truncated silently past the output limit. Chunking by measured token cost fixed it with zero jobs lost.

Cheap model, on purpose

This is a classification task. Claude Haiku handles it easily and keeps the run's cost negligible even at hundreds of postings.

reliability engineering

The one source that needed real engineering: Drushim

The other three sources are one HTTP call each. Drushim broke that pattern. Click through what it took to stabilize it.

01 failed

The sync call kept failing

›

With full details on (needed for the AI to read each posting), Drushim visits every listing individually. That pushes total run time past Apify's own ~300s limit on the synchronous endpoint.

02 failed

The async rewrite broke too

›

Switched to Apify's async API: start the run, poll status, fetch the dataset when done. Worked in testing, then failed quietly in production.

03 found

Root cause: a hidden platform limit

›

n8n Cloud's Code node has its own hard 60-second execution limit, separate from the workflow timeout setting. It was invisible until it showed up in the execution log.

04 resolved

Cleans up after itself

›

A failed call doesn't stop the run on Apify's side, it keeps eating concurrency quota. The node now aborts its own runs on timeout and pulls whatever the dataset already collected.

design decisions

Choices that weren't defaults

Two-tier filtering

Free regex first, AI second. They only overlap on genuinely ambiguous cases.

Built from what you ask

The AI's matching criteria come from whatever titles were requested that run, not a fixed list.

Two dedup layers

Same posting, two searched titles: deduped before the AI sees it. Same posting, two runs weeks apart: the Sheet remembers.

Picked by real usage

Each Apify actor was chosen by rating, review count, and real 30-day usage. Some 5-star actors had almost no active users.

What building it involved

Workflow automation

Multi-stage n8n pipeline: trigger, fan-out, filtering, batching, delivery. No custom loop code.

API integration

Four mismatched Apify schemas into one shape. Fixed several guessed field names along the way.

Prompt engineering

Moved from one call per job to measured batch sizing after a silent truncation bug.

Debugging

Traced a 322-vs-321 count mismatch back to expected dedup, not a bug.

Bilingual data handling

Regex and prompt both treat Hebrew and English postings as first-class.

Platform diagnosis

Found n8n's undocumented 60-second Code node limit by reading raw execution logs.
